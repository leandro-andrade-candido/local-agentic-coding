## 1–5. Isolamento, segredos, rede, limites, trava autonomous: BLOQUEADO

Sonda própria (`scratchpad/probe/probe.sh` e `probe2.sh`), container via `run-in-box.sh --no-llm` com um workdir descartável, passando no ambiente do host `GITHUB_TOKEN`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `SSH_AUTH_SOCK`, `AWS_SECRET_ACCESS_KEY`, `GH_TOKEN`:

- **Identidade/privilégio:** uid 1000(agent), `CapEff/CapPrm/CapBnd=0`, `NoNewPrivs=1`, `Seccomp=2`. `unshare -U`/`-Ur` → EPERM; `mount --bind` → "must be superuser"; nenhum setuid.
- **Escrita:** bloqueada em `/ /etc /usr /usr/local/bin /opt /opt/agents /run /run/agent-box /var /root /home /sys/fs/cgroup`. Graváveis só workdir, log-dir, `/tmp`, `/var/tmp`, `$HOME` (tmpfs).
- **`/proc/1/root`** aponta para a raiz **do container** (`/etc/hostname`=`agent-box`). `/home/leandro` ali é só o **scaffold** criado pelo Docker para o mount de `agents/` (dono `root`, criado no start): contém apenas `me/local/agents` (ro); `.ssh`, `.claude`, `.codex`, `.gitconfig`, `~/.config/local-agentic/llm-api-key` e o resto do repo (`eval/`, `sandbox/`) **ausentes**. Não é fuga — alarme descartado após verificação (`probe2.sh`). `/proc/1/environ` só revela o ambiente do próprio container.
- **docker.sock** ausente; sem CLI `docker`/`ssh`/`gh`. `/dev` mínimo; sem `dxg`/`nvidia`/`kvm`.
- **Segredos:** no ambiente do container, a única variável de padrão "segredo" é `LLM_API_KEY` (por desenho, para os agentes). `GITHUB_TOKEN`, `GH_TOKEN`, `ANTHROPIC/OPENAI_API_KEY`, `SSH_AUTH_SOCK`, `AWS_*` **não passam**.
- **Rede:** só `lo`. Conexões a `127.0.0.1:8080` (outro serviço local), `:22`, `::1:8080` e IPs do host → recusadas; DNS/internet → falha; `AF_VSOCK` e raw socket → EPERM; nenhum socket unix abstrato do host. O encaminhador tem destino **fixo** (`127.0.0.1:<porta do LLM_BASE_URL>`) definido no host; o container não escolhe porta nem destino. Confirmei que a porta 8080 é inalcançável.
- **Limites:** `memory.max`=8 GiB (3 GiB no teste), `memory.swap.max`=0, `pids.max`=2048 (512), `cpu.max` coerente.
- **Trava autonomous no host:** `require_box_for_autonomous` exige `AGENT_BOX=1` **e** (`/.dockerenv` ou `/run/.containerenv`). No host os dois estão ausentes e **não consigo criá-los** como uid 1000 (`/` e `/run` não graváveis). Dentro do container `/.dockerenv` existe (0 bytes, root). Trava correta.

## 6. Git do workdir executando na captura do diff: BLOQUEADO (contido)

Controle positivo (`scratchpad/posctl`): um `.git/config` com `core.fsmonitor` apontando para um script que grava um canário **executa no host** quando a captura do diff roda **sem** o wrapper (confirma meu mecanismo de canário e por que a captura precisa ser conteinerizada). Com `EVAL_WRAPPER`, a captura (`box_post`) roda no container: o `fsmonitor`/filtros do agente executam **lá dentro** (vi os erros tentando escrever no caminho do host, que só existe fora) e **nenhum canário `HOST-PWNED` foi criado no host**. Essa parte do desenho funciona.

## 7. `cp -r agent-logs` e `result.py` seguem symlinks do agente: VULNERÁVEL

Repliquei os passos de host do `eval/run.sh` posteriores ao agente (linhas 149 e 199), que **não são conteinerizados**, contra um workdir/`agent-logs` maliciosos. O agente controla diretamente `$work/agent-logs` (montado `--rw` no container do agente) e, via execução de código em `box_post` (item 6), qualquer symlink dentro de `$out`.

- **`cp -r "$work/agent-logs" "$out/agent-logs"` (host, linha 149):** o `cp` do GNU 9.4 **preserva** symlinks da origem (não deref) — então não há exfiltração em massa. Mas:
  - **Leitura arbitrária (`scratchpad/hostside`):** o agente põe `agent-logs/agent-metrics.json` como symlink para um arquivo do host. O `cp -r` o copia como symlink e depois o `result.py` faz `open()` nele, **seguindo o symlink**, e grava o conteúdo (se for JSON válido) em `agent.metrics` do `result.json`. Confirmado: `{"stolen":"HOST_SECRET_VIA_SYMLINK"}` apareceu no `result.json`. Não precisa de execução em `box_post` — é direto.
  - **Escrita arbitrária (`scratchpad/chain`):** se `$out/agent-logs` já existe como symlink para um diretório do host (criado pelo código do `.git/config` em `box_post`, que acha `$out` pelo `/proc/self/mountinfo`), o `cp -r` do host **escreve através** dele os arquivos do agente em `<dir-do-host>/agent-logs/`. Confirmado end-to-end com o `run-in-box.sh` real.
- **`result.py` (host, linha 199) — sobrescrita arbitrária (`scratchpad/e2e.sh`):** `box_post` (git do agente via `core.fsmonitor`, rodando no container com `$out` montado `--rw`) cria `$out/result.json` como symlink para um arquivo-vítima do host. Depois o `result.py` do host faz `open(".../result.json","w")`, **segue o symlink e sobrescreve o arquivo do host** com o conteúdo do `result.json` (que inclui strings controladas pelo agente via `agent-metrics.json`). Confirmado end-to-end: um `~/.bashrc` simulado foi sobrescrito. Apontando para `~/.bashrc`, `~/.profile`, `~/.gitconfig`, etc., isso vira **execução de código no host** na próxima sessão do usuário.

Causa-raiz: depois do agente, o host (a) copia `agent-logs` preservando symlinks e depois os **segue** (`result.py`), e (b) escreve/sobrescreve dentro de `$out` **sem checar se os caminhos viraram symlinks** — e `box_post` roda o git do workdir com `fsmonitor`/filtros/hooks do agente **habilitados**, podendo plantar esses symlinks em `$out`.

O `escape-tests.sh` não cobre esse caminho (não planta symlink em `agent-logs` nem `.git/config` malicioso processado por `box_post`+host), por isso passa 137/137.

## Problemas

### Bloqueante

1. **Sobrescrita/escrita de arquivo arbitrário no host a partir de um workdir malicioso (item 7).** Um agente malicioso (o caso que o `agent-box` existe para conter) consegue, via `.git/config` processado por `box_post` + `cp -r`/`result.py` do host, escrever conteúdo controlado em locais graváveis pelo usuário e sobrescrever arquivos (ex.: `~/.bashrc`) → execução de código no host. Quebra "no eval, nada do workdir roda no host depois do agente".
   - **Correção (camadas):**
     - Em `box_post`, rodar o git com a config do agente neutralizada (como o próprio README recomenda para revisão): `git -c core.fsmonitor=false -c core.hooksPath=/dev/null --no-ext-diff ...` e desligar filtros (ou `GIT_CONFIG_SYSTEM`/`GIT_CONFIG_GLOBAL=/dev/null` **mais** override dos `filter.*`). Isso remove a execução de código que planta os symlinks em `$out`.
     - Antes de qualquer passo de host que leia/escreva em `$out`, **sanear symlinks**: `find "$out" -type l -delete` (e remover/validar `$out/result.json`, `$out/meta.json`, `$out/agent-logs` antes de criá-los).
     - `result.py`: abrir saída e entradas com `O_NOFOLLOW` (gravar `result.json` via `os.open(O_CREAT|O_EXCL|O_WRONLY|O_NOFOLLOW)` num temporário + `os.replace`); recusar symlink em `agent-metrics.json`.
     - Melhor ainda: fazer a cópia de `agent-logs` e a montagem do `result.json`/`meta.json` **dentro de um container** (onde os caminhos do host não existem), como já se faz com a captura do diff e as verificações.

### Importante

2. **Leitura de arquivo arbitrário do host via `result.py` seguindo symlink em `agent-logs/agent-metrics.json` (item 7).** Não exige execução em `box_post` — o agente planta o symlink direto em `$work/agent-logs`. Conteúdo (se JSON válido) vaza para `result.json`, que fica em `eval/runs/` e pode ser commitado/compartilhado.
   - **Correção:** mesma sanitização de symlinks no `cp` (`find "$out/agent-logs" -type l -delete` após copiar, ou copiar só arquivos regulares) + `O_NOFOLLOW` no `result.py`.

### Menor

3. **Ponto cego do `escape-tests.sh`:** não há teste de regressão para symlinks em `agent-logs` nem para `.git/config` malicioso atravessando `box_post` → `cp`/`result.py` do host. Adicionar um caso que planta esses symlinks e verifica que nenhum arquivo fora das montagens é lido/escrito.
4. **`rm -rf "$wd/.venv"`/`node_modules` e `rm -rf "$work"` (limpeza, host) rodam sobre caminhos do agente.** Não é furo (o `rm -rf` desfaz o symlink, não segue), mas vale um comentário/teste para não regredir.
5. **Observação (não é fuga):** `run-in-box.sh` usa o `docker` do host com o ambiente do operador (ex.: `DOCKER_HOST`); é comportamento normal do CLI e não vaza para o container. Mencionado só porque me custou um falso "imagem não encontrada" no teste.
