## E3: smoke test with Qwen3.5-4B

**Model and server**
- Model: `Qwen3.5-4B-UD-Q4_K_XL.gguf`, 2.9 GB, SHA-256 checked by `scripts/fetch-model.sh`.
- The server loaded in 1.5 s, with all layers on the GPU.

**Benchmark** (`llama-bench`, 3 repetitions, everything on the GPU, flash attention):

| Test | tok/s |
|---|---|
| pp512 (prompt reading) | 3,733.65 ± 89.33 |
| tg128 (generation) | 82.10 ± 1.46 |

**Tool calls** (`scripts/smoke_test.py`)
- Cases: `read_file`, `run_command`, `edit_file` with quotes, plus a full round trip (call → tool result → final answer).
- Endpoints: OpenAI `/v1/chat/completions` and Anthropic `/v1/messages`.

| Round | Result | Note |
|---|---|---|
| 1st (original test) | 7 of 8 | In the edit case on the OpenAI endpoint, the model called `read_file(app.py)` before editing, with explicit reasoning ("first read the file... then use edit_file"). The call is valid and the behavior is correct for an agent. |
| Test adjustment | — | The edit request now states the file contents, so that editing directly is the expected action. |
| 3 rounds after the adjustment | 20 of 21 with the expected action | In the single exception, the 4B read before editing again. |

**Conclusion**
- **21 of 21 tool calls with a valid format** on both endpoints: the runtime parser is OK.
- The only divergence is a choice made by the small model, not a runtime failure. I did not keep tuning the test to reach 100%, because that would hide real behavior.
- **Limitation pointed out by the verifier:** the outputs of these rounds were not saved, and the original script did not classify the format of the calls. The numbers "7 of 8", "20 of 21" and "21 of 21" cannot be checked after the fact. The valid evidence is the verifier's independent battery (below).
- `scripts/smoke_test.py` was replaced by `scripts/tool_calls.py` (see fixes) and is not in the repository.

## Problems found and solutions

| Problem | Solution |
|---|---|
| Port 8080 (a common default) is already used by another local service | Server on 9931, the llama.cpp v0.7.0 default, recorded in `versions.env` |
| `pkill -f "<pattern>"` matched the shell's own command line and killed the command | Stop the server by PID (`pgrep -f` with a pattern that does not appear in its own command, or a PID saved at startup). The E5 systemd unit solves this for good. |
| The first edit test was too rigid and failed correct behavior | Case rewritten; the reason is in a comment in the script |

## Independent verification and fixes

Full report in [`docs/verifications/E1-E3.md`](../verifications/E1-E3.md). Verdict: **E1, E2 and E3 approved, nothing blocking**.
- **Verifier's own battery:** 60 of 60 with no runtime or parser failure, including streaming, integer arguments, arrays, multiline strings and no-tool cases. Round trip and parallel calls: 3 of 3 on each endpoint.
- **Benchmark reproduced:** tg128 82.59 tok/s.

Findings and what was done:

| Finding | Severity | Action |
|---|---|---|
| Server without an API key and with open CORS, reachable from the Windows browser | important | Carried to E5: `--api-key-file` and restricted CORS |
| The smoke test did not cover streaming, did not separate parser from model choice, did not pin sampling and did not save output | important | The verifier's battery was adopted as `scripts/tool_calls.py`. It gained the round trip and parallel calls on both endpoints, `--api-key`, `--json-out` and exit code 1 only for `RUNTIME`/`TRUNCADO`. The classifier was tested with synthetic responses of the four classes. The first real run is left for E5, because the GPU is busy with E4. |
| `install-llama-cpp.sh` exited with success if the build directory existed but was incomplete | important | The `.complete` marker is only created after extraction. A directory without it is redone with `mv -T`. Added a lock (`flock`), a cleanup `trap`, `chmod 755` and a hash check on the `.part` before the final name. Tested in an isolated `HOME`: incomplete directory redone, a new run instant, no leftovers. |
| `fetch-model.sh` got stuck if the `.part` had the right size and the wrong hash | minor | The invalid partial file is discarded and downloaded again once. Tested with a small file from the same HF repository. |
| Download without a pinned revision (`resolve/main`) | minor | New `revisao` column in `models.tsv`; the download uses `resolve/<sha>` |
| No lock against simultaneous runs | minor | `flock` in both scripts |
| Running the installer again undid a manual rollback | minor | Rollback documented through `versions.env`, which is the single source of truth |
| Build pinned about 1 h after publication | minor | Kept: it was verified and the hash is pinned. If E4 shows a regression, the way back is the v0.7.0 build. |
| E3 outputs not saved | minor | From here on, every test run saves its output in `logs/` or `bench/raw/` |

## Items carried to E4 and E5

- **Server defaults:** `n_slots = 4` and `n_threads = 8`. For the agents, use `-np 1` and calibrate `-t`/`-tb` in E4.
- **Security:** the server warns that there is no API key and that CORS is open. Since WSL forwards localhost to Windows, a page opened in the browser could call the model. In E5, use `--api-key` with the key kept outside git and restrict CORS.
- **Metrics:** `--metrics` works and will be used by the validation runner.
