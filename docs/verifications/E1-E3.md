### Rollback

I simulated it in an isolated copy in the scratchpad, with the prefix pointing there:

```
cp -al b11982 b11000-antigo; ln -sfn b11000-antigo current   →  current/llama-server runs and ldd resolves via current/
ln -sfn b11982 current                                        →  back OK
```

- Switching the link is enough, because the `$ORIGIN` RUNPATH follows the link path.

### Model behavior, not a runtime failure

In 6 of 12 `write_file` calls, the content came without the final `\n`. I checked the raw output with `/apply-template` plus `/completion`:

```
#1 …    return 0\n\n</parameter>   → content ends in "\n"
#2 …    return 0\n</parameter>     → content ends without "\n"
```

- Qwen's XML format removes exactly one newline before `</parameter>`.
- The model sometimes emits one newline and sometimes two, so the difference comes from the model. The parser follows the format.
- Practical consequence: agents may write files without the final newline. The E7 formatter fixes this.

## Script review

### `scripts/install-llama-cpp.sh`

- **Bug confirmed (I3).** If `$dest` already exists but has no executable `llama-server`, `mv "$tmp" "$dest"` moves the temporary directory **inside** `$dest`. The script prints "instalado" and exits with 0. I reproduced it in an isolated copy:
  ```
  rm $P/b11982/llama-server; bash install-llama-cpp.sh
  instalado: …/b11982 (current -> b11982)   T3 exit=0
  …/b11982/.install-iNXC                     ← nested temporary directory
  llama-server AUSENTE em current/ apesar de exit 0
  ```
- There is no cleanup `trap`. If `tar` fails midway, `$LLAMA_CPP_PREFIX/.install-XXXX` is left behind (M4).
- `fetch()` moves the `.part` to the final name **before** checking the hash. A corrupted tarball stays in the cache and every run fails the same way, without saying what to do (M5).
- The installed directory ends up with `drwx------` permissions, inherited from `mktemp -d`, while the tarball uses 0755 (M7). It does not affect use by a single user.
- `ln -sfn` is not atomic (it deletes and recreates the link). The risk is negligible now, but it starts to matter once a service is restarting (M6).
- **Positive points:**
  - The hash is checked before extracting.
  - Extraction happens in a temporary directory and the final `mv` is atomic on the normal path.
  - The link is relative.
  - Old builds are kept.

### `scripts/fetch-model.sh`

- **Confirmed (M1).** A `.part` with the right size and the wrong content locks the script forever. Since the size matches, it does not download again, and the hash always fails. I reproduced it offline:
  ```
  rodada 1 exit=1  (…fake.gguf.part: FAILED)
  rodada 2 exit=1  (…fake.gguf.part: FAILED)   ← never downloads again, no instruction to the user
  ```
  The normal path worked: with the `.part` complete and correct, the script checked and installed, and running again exited with 0.
- The download uses `resolve/main`, without pinning a revision (M2). There are two risks:
  - If Unsloth publishes a new GGUF, which is common after template fixes, resuming with `-C -` joins bytes from two versions.
  - Future downloads start failing on the hash with no explanation.
  The hash protects integrity, but not reproducibility. Current revisions: `unsloth/Qwen3.5-4B-GGUF@e87f176479d0855a907a41277aca2f8ee7a09523` and `unsloth/Qwen3.6-35B-A3B-GGUF@a483e9e6cbd595906af30beda3187c2663a1118c`.
- There is no lock (`flock`). Two simultaneous runs of the same alias append data to the same `.part` (M3).
- **Positive point:** the final file only appears after checking size and SHA-256.

### `scripts/smoke_test.py` (I2, M8)

- It does not test streaming. Qwen Code, OpenCode, Pi and Claude Code use SSE, and the incremental tool-call parser is a different code path. In this verification streaming worked (30/30), but the script, which is the regression test for updating llama.cpp, would not catch a break in that path.
- It does not separate parser failure from model choice:
  - When `arguments` comes with invalid JSON, `json.loads` raises an exception and the script aborts, without classifying.
  - Only the first call is examined.
  - It does not check `finish_reason`/`stop_reason` or whether markup is leaking into the text.
- Three coverages are missing:
  - typed arguments (integer, array, boolean);
  - a case where no tool should be called;
  - the round trip with `tool_result` on the Anthropic endpoint.
- Sampling is not pinned, so the result varies between runs. As a health check (E5), the test would fail occasionally for no real reason.

## Security (current state)

### Server without authentication and with CORS that reflects any origin (I1)

```
$ curl -i -X OPTIONS …/v1/chat/completions -H 'Origin: https://site-malicioso.example' …
Access-Control-Allow-Origin: https://site-malicioso.example
Access-Control-Allow-Credentials: true
$ powershell.exe … Invoke-WebRequest http://127.0.0.1:9931/health   # run from WSL, on Windows
{"status":"ok"}
```

- The server answers from Windows, and CORS accepts any origin with credentials.
- Any page opened in the Windows browser can send prompts and read the responses. The consequences:
  - misuse of the GPU and denial of service;
  - discarding of the agent's context cache;
  - in the future, interference with measurements.
- What is not exposed:
  - In this build, `/slots` shows only counters and parameters, not the prompt text.
  - `POST /props` is disabled (`--props` was not used).
  - The server listens only on 127.0.0.1, so it is not exposed to the local network.
- The builder had already recorded this as an E5 pending item. I add that the server **reflects the origin with `Allow-Credentials: true`**, which is worse than a plain `*`.

### Recent release (M9)

- Release `b11982` was published at 12:17 UTC and downloaded about 1 h later.
- The SHA-256 guarantees that the file is the same one published on GitHub, but not that the build is free of regressions.

### What is fine

- Scripts with `set -euo pipefail`.
- Hash checked before extracting and before installing the model.
- Nothing uses `sudo`.
- `.env` and `*.local*` stay out of git.
