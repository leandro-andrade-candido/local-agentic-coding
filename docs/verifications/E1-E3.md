
## Revisão dos scripts

### `scripts/install-llama-cpp.sh`

- **Bug confirmado (I3).** Se `$dest` já existe mas não tem `llama-server` executável, o `mv "$tmp" "$dest"` move o temporário para **dentro** de `$dest`. O script imprime "instalado" e sai com 0. Reproduzi numa cópia isolada:
  ```
  rm $P/b11982/llama-server; bash install-llama-cpp.sh
  instalado: …/b11982 (current -> b11982)   T3 exit=0
  …/b11982/.install-iNXC                     ← temporário aninhado
  llama-server AUSENTE em current/ apesar de exit 0
  ```
- Não há `trap` de limpeza. Se o `tar` falhar no meio, sobra `$LLAMA_CPP_PREFIX/.install-XXXX` (M4).
- `fetch()` move o `.part` para o nome final **antes** de conferir o hash. Um tarball corrompido fica no cache e toda execução falha do mesmo jeito, sem dizer o que fazer (M5).
- O diretório instalado fica com permissão `drwx------`, herdada do `mktemp -d`, enquanto o tarball usa 0755 (M7). Não afeta o uso por um único usuário.
- `ln -sfn` não é atômico (apaga e recria o link). O risco é desprezível agora, mas passa a contar quando houver serviço reiniciando (M6).
- **Pontos positivos:**
  - O hash é conferido antes de extrair.
  - A extração acontece em diretório temporário e o `mv` final é atômico no caminho normal.
  - O link é relativo.
  - Builds antigos são mantidos.

### `scripts/fetch-model.sh`

- **Confirmado (M1).** Um `.part` com o tamanho certo e o conteúdo errado trava o script para sempre. Como o tamanho bate, ele não baixa de novo, e o hash sempre falha. Reproduzi offline:
  ```
  rodada 1 exit=1  (…fake.gguf.part: FAILED)
  rodada 2 exit=1  (…fake.gguf.part: FAILED)   ← nunca baixa de novo, sem instrução ao usuário
  ```
  O caminho normal funcionou: com o `.part` completo e correto, o script conferiu e instalou, e rodar de novo saiu com 0.
- O download usa `resolve/main`, sem fixar uma revisão (M2). Há dois riscos:
  - Se o Unsloth publicar um GGUF novo, o que é comum depois de correções de template, a retomada com `-C -` junta bytes de duas versões.
  - Downloads futuros passam a falhar no hash sem explicação.
  O hash protege a integridade, mas não a reprodutibilidade. Revisões atuais: `unsloth/Qwen3.5-4B-GGUF@e87f176479d0855a907a41277aca2f8ee7a09523` e `unsloth/Qwen3.6-35B-A3B-GGUF@a483e9e6cbd595906af30beda3187c2663a1118c`.
- Não há trava (`flock`). Duas execuções simultâneas do mesmo alias acrescentam dados ao mesmo `.part` (M3).
- **Ponto positivo:** o arquivo final só aparece depois de conferir tamanho e SHA-256.

### `scripts/smoke_test.py` (I2, M8)

- Não testa streaming. Qwen Code, OpenCode, Pi e Claude Code usam SSE, e o parser incremental de tool calls é outro caminho de código. Nesta verificação o streaming funcionou (30/30), mas o script, que é o teste de regressão para atualizar o llama.cpp, não pegaria uma quebra nesse caminho.
- Não separa falha de parser de escolha do modelo:
  - Quando `arguments` vem com JSON inválido, o `json.loads` lança exceção e o script aborta, sem classificar.
  - Só a primeira chamada é examinada.
  - Não confere `finish_reason`/`stop_reason` nem se há markup vazando no texto.
- Faltam três coberturas:
  - argumentos tipados (inteiro, array, booleano);
  - um caso em que nenhuma ferramenta deve ser chamada;
  - a ida e volta com `tool_result` no endpoint Anthropic.
- A amostragem não é fixada, então o resultado varia entre execuções. Como verificação de saúde (E5), o teste falharia ocasionalmente sem motivo real.

## Segurança (estado atual)

### Servidor sem autenticação e com CORS que reflete qualquer origem (I1)

```
$ curl -i -X OPTIONS …/v1/chat/completions -H 'Origin: https://site-malicioso.example' …
Access-Control-Allow-Origin: https://site-malicioso.example

```

- O servidor responde a partir do Windows, e o CORS aceita qualquer origem com credenciais.
- Qualquer página aberta no navegador do Windows pode mandar prompts e ler as respostas. As consequências:
  - uso indevido de GPU e negação de serviço;
  - descarte do cache de contexto do agente;
  - no futuro, interferência nas medições.
- O que não está exposto:
  - Neste build, `/slots` mostra só contadores e parâmetros, não o texto do prompt.
  - `POST /props` está desligado (`--props` não foi usado).
  - O servidor escuta só em 127.0.0.1, então não fica exposto à rede local.
- O builder já registrou isso como pendência da E5. Acrescento que o servidor **reflete a origem com `Allow-Credentials: true`**, o que é pior do que um `*` simples.

- O SHA-256 garante que o arquivo é o mesmo publicado no GitHub, mas não que o build esteja livre de regressões.
