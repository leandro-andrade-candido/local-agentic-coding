## 1–5. Isolation, secrets, network, limits, autonomous lock: BLOCKED

My own probe (`scratchpad/probe/probe.sh` and `probe2.sh`), container via `run-in-box.sh --no-llm` with a disposable workdir, passing `GITHUB_TOKEN`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `SSH_AUTH_SOCK`, `AWS_SECRET_ACCESS_KEY`, `GH_TOKEN` in the host environment:

- **Identity/privilege:** uid 1000(agent), `CapEff/CapPrm/CapBnd=0`, `NoNewPrivs=1`, `Seccomp=2`. `unshare -U`/`-Ur` → EPERM; `mount --bind` → "must be superuser"; no setuid.
- **Write:** blocked in `/ /etc /usr /usr/local/bin /opt /opt/agents /run /run/agent-box /var /root /home /sys/fs/cgroup`. Writable only workdir, log-dir, `/tmp`, `/var/tmp`, `$HOME` (tmpfs).
- **`/proc/1/root`** points to the **container's** root (`/etc/hostname`=`agent-box`). `~` there is only the **scaffold** created by Docker for the `agents/` mount (owner `root`, created at start): it contains only `me/local/agents` (ro); `.ssh`, `.claude`, `.codex`, `.gitconfig`, `~/.config/local-agentic/llm-api-key` and the rest of the repo (`eval/`, `sandbox/`) are **absent**. Not an escape — alarm dismissed after verification (`probe2.sh`). `/proc/1/environ` only reveals the container's own environment.
- **docker.sock** absent; no `docker`/`ssh`/`gh` CLI. Minimal `/dev`; no `dxg`/`nvidia`/`kvm`.
- **Secrets:** in the container's environment, the only variable matching a "secret" pattern is `LLM_API_KEY` (by design, for the agents). `GITHUB_TOKEN`, `GH_TOKEN`, `ANTHROPIC/OPENAI_API_KEY`, `SSH_AUTH_SOCK`, `AWS_*` **do not pass through**.
- **Network:** only `lo`. Connections to `127.0.0.1:8080` (another local service), `:22`, `::1:8080` and host IPs → refused; DNS/internet → fail; `AF_VSOCK` and raw socket → EPERM; no abstract unix socket from the host. The forwarder has a **fixed** destination (`127.0.0.1:<LLM_BASE_URL port>`) set on the host; the container chooses neither port nor destination. I confirmed that port 8080 is unreachable.
- **Limits:** `memory.max`=8 GiB (3 GiB in the test), `memory.swap.max`=0, `pids.max`=2048 (512), `cpu.max` coherent.
- **Autonomous lock on the host:** `require_box_for_autonomous` requires `AGENT_BOX=1` **and** (`/.dockerenv` or `/run/.containerenv`). On the host both are absent and **I cannot create them** as uid 1000 (`/` and `/run` are not writable). Inside the container `/.dockerenv` exists (0 bytes, root). Correct lock.

## 6. Workdir git running during the diff capture: BLOCKED (contained)

Positive control (`scratchpad/posctl`): a `.git/config` with `core.fsmonitor` pointing to a script that writes a canary **runs on the host** when the diff capture runs **without** the wrapper (this confirms my canary mechanism and why the capture needs to be containerized). With `EVAL_WRAPPER`, the capture (`box_post`) runs in the container: the agent's `fsmonitor`/filters run **in there** (I saw the errors when trying to write to the host path, which only exists outside) and **no `HOST-PWNED` canary was created on the host**. This part of the design works.

## 7. `cp -r agent-logs` and `result.py` follow the agent's symlinks: VULNERABLE

I replicated the host steps of `eval/run.sh` after the agent (lines 149 and 199), which are **not containerized**, against a malicious workdir/`agent-logs`. The agent directly controls `$work/agent-logs` (mounted `--rw` in the agent's container) and, through code execution in `box_post` (item 6), any symlink inside `$out`.

- **`cp -r "$work/agent-logs" "$out/agent-logs"` (host, line 149):** GNU `cp` 9.4 **preserves** symlinks from the source (no deref) — so there is no bulk exfiltration. But:
  - **Arbitrary read (`scratchpad/hostside`):** the agent makes `agent-logs/agent-metrics.json` a symlink to a host file. `cp -r` copies it as a symlink and then `result.py` does `open()` on it, **following the symlink**, and writes the content (if it is valid JSON) into `agent.metrics` of `result.json`. Confirmed: `{"stolen":"HOST_SECRET_VIA_SYMLINK"}` showed up in `result.json`. It does not need execution in `box_post` — it is direct.
  - **Arbitrary write (`scratchpad/chain`):** if `$out/agent-logs` already exists as a symlink to a host directory (created by the `.git/config` code in `box_post`, which finds `$out` through `/proc/self/mountinfo`), the host's `cp -r` **writes through** it the agent's files into `<host-dir>/agent-logs/`. Confirmed end-to-end with the real `run-in-box.sh`.
- **`result.py` (host, line 199) — arbitrary overwrite (`scratchpad/e2e.sh`):** `box_post` (the agent's git via `core.fsmonitor`, running in the container with `$out` mounted `--rw`) creates `$out/result.json` as a symlink to a victim file on the host. Then the host's `result.py` does `open(".../result.json","w")`, **follows the symlink and overwrites the host file** with the content of `result.json` (which includes agent-controlled strings via `agent-metrics.json`). Confirmed end-to-end: a simulated `~/.bashrc` was overwritten. Pointing to `~/.bashrc`, `~/.profile`, `~/.gitconfig`, etc., this becomes **code execution on the host** in the user's next session.

Root cause: after the agent, the host (a) copies `agent-logs` preserving symlinks and then **follows** them (`result.py`), and (b) writes/overwrites inside `$out` **without checking whether the paths became symlinks** — and `box_post` runs the workdir's git with the agent's `fsmonitor`/filters/hooks **enabled**, which can plant those symlinks in `$out`.

`escape-tests.sh` does not cover this path (it does not plant a symlink in `agent-logs` nor a malicious `.git/config` processed by `box_post`+host), which is why it passes 137/137.

## Problems

### Blocking

1. **Arbitrary host file write/overwrite from a malicious workdir (item 7).** A malicious agent (the case `agent-box` exists to contain) can, via a `.git/config` processed by `box_post` + the host's `cp -r`/`result.py`, write controlled content to user-writable locations and overwrite files (e.g. `~/.bashrc`) → code execution on the host. It breaks "in the eval, nothing from the workdir runs on the host after the agent".
   - **Fix (layers):**
     - In `box_post`, run git with the agent's config neutralized (as the README itself recommends for review): `git -c core.fsmonitor=false -c core.hooksPath=/dev/null --no-ext-diff ...` and turn off filters (or `GIT_CONFIG_SYSTEM`/`GIT_CONFIG_GLOBAL=/dev/null` **plus** an override of the `filter.*` entries). This removes the code execution that plants the symlinks in `$out`.
     - Before any host step that reads/writes in `$out`, **sanitize symlinks**: `find "$out" -type l -delete` (and remove/validate `$out/result.json`, `$out/meta.json`, `$out/agent-logs` before creating them).
     - `result.py`: open output and inputs with `O_NOFOLLOW` (write `result.json` via `os.open(O_CREAT|O_EXCL|O_WRONLY|O_NOFOLLOW)` to a temporary file + `os.replace`); refuse a symlink in `agent-metrics.json`.
     - Even better: do the copy of `agent-logs` and the assembly of `result.json`/`meta.json` **inside a container** (where host paths do not exist), as is already done for the diff capture and the checks.

### Important

2. **Arbitrary host file read via `result.py` following a symlink in `agent-logs/agent-metrics.json` (item 7).** It does not require execution in `box_post` — the agent plants the symlink directly in `$work/agent-logs`. The content (if valid JSON) leaks into `result.json`, which sits in `eval/runs/` and may be committed/shared.
   - **Fix:** the same symlink sanitization in the `cp` (`find "$out/agent-logs" -type l -delete` after copying, or copy only regular files) + `O_NOFOLLOW` in `result.py`.

### Minor

3. **Blind spot in `escape-tests.sh`:** there is no regression test for symlinks in `agent-logs` nor for a malicious `.git/config` going through `box_post` → the host's `cp`/`result.py`. Add a case that plants those symlinks and checks that no file outside the mounts is read/written.
4. **`rm -rf "$wd/.venv"`/`node_modules` and `rm -rf "$work"` (cleanup, host) run over agent paths.** Not a hole (`rm -rf` removes the symlink, it does not follow it), but it deserves a comment/test so it does not regress.
5. **Observation (not an escape):** `run-in-box.sh` uses the host's `docker` with the operator's environment (e.g. `DOCKER_HOST`); this is normal CLI behavior and does not leak into the container. Mentioned only because it cost me a false "image not found" in the test.
